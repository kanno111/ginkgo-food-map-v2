### A步最小发布流程（原文本阶段范围）

以下保留A步最初的文本范围和验收依据，其中“首步不支持图片”仅描述当时的交付边界。当前发布已接受最多五个有序photoIds，具体协议以[接口文档](../api.md)为准，图片进展见第7节；无需恢复为纯文本限制。

1. 前端或接口调用者生成一次提交UUID，发送餐厅ID、四维分、推荐态度和正文，具体请求见第5.1节。
2. 后端从当前登录会话取作者；检查餐厅存在且未删除、四维完整/0–10半分、推荐必填、正文规范化后5–500码点。
3. 同一数据库事务锁父餐厅、校验幂等、保留旧点评并新增本条，更新统计。首次评价增加人数，再次评价只替换本人计分，条数仍增加。
4. 事务提交后首次返回201和新点评ID；网络重试同账号/同UUID/同内容返回200及原ID，内容不同返回409。失败保留正文和原UUID，不提前宣告成功。

A步需要V5补独立计分人数和查询索引，详见第4.2节；不改已执行V1–V4。先不实现读取、历史、图片、回复、删除、榜单或预测接口，前端现已接POST并显示回执，但明确提示尚无读取/评分展示，不冒充完整闭环。使用隔离数据库集成测试和接口调用验收。

最小验收：首次成功落一条且统计正确；同人再次发布保留旧条但只更新一份评分；同次重试不重复入库/计分；匿名或非法参数被拒绝；已删餐厅不能写；统计失败时点评同时回滚。并发验证至少包含同UUID重复提交、同人同店更新及与删店竞争。

图片/OSS、单层回复、本人/管理员删除及图片清理分步骤继续实现，不从评价阶段目标中删除。首步不开放这些写接口，不静默丢掉照片后只发布文字；已有附图草稿必须明确提示尚不支持并保留，用户主动移除后才可发文本。原前端独立演示保留，与真实接口数据隔离。

不新增评价编辑、软删除/恢复、点赞、多级回复、每日配额、生产导入或新的中间件。V5已在本地开发库执行，不操作生产库；未提交、推送或部署。

## 4. 规则与数据调整建议

### 4.1 最新记录与计分

- 每个(restaurant_id, author_user_id)最多一条记录参与计分。最新按服务端created_at DESC、id DESC确定，时间相同以ID定序；客户端不能指定发布时间、作者或计分状态。
- 时间在取得父店锁后的插入阶段生成；实现时应保证同人的新记录时间不早于旧记录时间，避免数据库时钟回拨使新点评意外成为历史。可取数据库当前时间与旧代表时间的较大者，仍以新ID打破同时间平局。
- review_count表示保留的点评总条数；新增participant_count表示有有效点评的独立账号数。四维sum、overall_score_sum和recommend_count只累加各人的最新点评。
- 四维均分=sum/participant_count，推荐率=recommend_count/participant_count。综合分继续沿用“单条四维均分HALF_UP两位，再对代表点评求均分”，不擅自变更为另一种总分口径。杯型用未做展示舍入的精确值比较阈值。
- 无人评价时所有对外分数和推荐率为null；有评价的0分是有效评分。前端分别展示“点评条数”和“评价人数”。同名不同账号始终独立。

### 4.2 已执行V5，保留V1–V4

1. statistics新增participant_count；约束调整为recommend_count <= participant_count <= review_count，所有累计值在0至10×participant_count之间。
2. reviews补充(restaurant_id, author_user_id, created_at, id)索引，支持取本人最新、按人归组及历史游标。
3. 在迁移中按真实现存reviews重建每店的总条数、人数与代表评分；不能假定生产没有评价或一律清零。对缺失统计行的餐厅补行，包括已软删除餐厅；公开查询仍隐藏删除店。
4. 验证空库、V4升级、有同人多评的夹具及Flyway重复启动不新增迁移。MySQL DDL不承诺整段事务回滚，升级前核对备份及失败处理；V5本地升级及重复迁移验证已完成，生产升级以实际发布为准。

首步先用现有reviews及复合索引求最新记录，不额外建立当前点评指针表或is_current标记，避免增加多份状态。大店分组读取的成本通过真实SQL执行计划和数据量验证；若后续证明需要独立读模型，再根据证据演进。

## 5. 拟定HTTP协议

下表A步POST及B1主列表GET已实现，正式协议见[接口文档第14节](../api.md#14-最简文本点评发布)和[第15节](../api.md#15-点评按作者分组读取)；历史与上下文仍为拟定协议。ID均为字符串，时间UTC，响应复用success/code/message/data/timestamp。

| 方法与路径 | 权限 | 用途 | 步骤 |
| --- | --- | --- | --- |
| POST /api/restaurants/{restaurantId}/reviews | 登录 | 发布文本/最多五图点评，不覆盖旧记录 | A及已完成图片扩展 |
| GET /api/restaurants/{restaurantId}/reviews | 公开 | 每位作者一张最新主卡片，分组分页 | B1已实现 |
| GET /api/restaurants/{restaurantId}/reviews/authors/{authorId}/history | 公开 | 指定作者在该店的历史记录游标分页 | C |
| GET /api/restaurants/{restaurantId}/reviews/me/context | 登录 | 当前账号在该店的计分记录及预测所需快照 | C |

### 5.1 发布请求与结果

```json
{
  "clientRequestId": "d6fb79a2-6866-41ae-9c38-13d239668c21",
  "scores": { "taste": 8, "value": 7.5, "service": 7, "ambience": 8 },
  "recommended": true,
  "body": "这次出餐很快，分量也比较足，下次还会来。"
}
```

- 四维均必填，0–10且步进0.5，用BigDecimal验证，不能先舍入再接收非法值；推荐必填布尔值。
- 正文按Unicode码点计数，首尾空白规范化后5–500字，作为纯文本。UUID要求规范有效；拒绝客户端指定author、score总分、scoringStatus和任意媒体URL。
- A步最初只接受文本；当前图片扩展已接受最多五个有序photoIds，提交前必须全部上传成功。photos、任意图片URL和其他不支持字段仍拒绝，不能静默丢图。空图沿用旧文本摘要，带图采用版本化摘要，保持既有请求重试兼容。
- 首次提交HTTP 201；同账号同UUID且规范化内容相同，HTTP 200返回原reviewId与replayed=true，不再写入或计分。成功data只包含reviewId、restaurantId、replayed，前端再读当前权威数据，不将旧请求的统计快照覆盖新状态。
- 同账号同UUID但餐厅、分数、推荐或规范化正文不同，HTTP 409 / REVIEW_REQUEST_CONFLICT。不同UUID即使正文相同也是不同业务提交，不新增“内容必须唯一”的规则。
- 首步不引入业务冷却或每日限评；幂等不等于反刷，保留现有账号安全边界，限流另行审核。

### 5.2 分组读取与历史（B/C步，不属于基础发布）

- 主列表以作者组分页，每页默认8组、最多50组；按当前代表点评(createdAt,id)倒序。totalGroups与totalReviews分别返回，不能先分页普通点评再在前端合并。
- 每组返回author公开信息、currentReview完整展示数据、historyCount及nextHistoryCursor，不内嵌无限历史。currentReview包括ID、四维、推荐、正文、服务端时间、单条综合分/杯型及最多五个有序图片引用；图片复用已实现的正式照片接口，不暴露OSS对象键或凭证。当前记录scoringStatus=current，历史记录为history，状态由服务端给出。B1可返回历史游标，历史接口和展开能力在C1开放前不启用。
- 点击展开才读取历史：默认5条、最多20条，以(createdAt,id)的排他游标取下一段；返回hasMore和nextCursor。所有游标都验证格式及所属餐厅/作者，不接收SQL片段。
- 历史请求返回currentReviewId；若与主卡片不同，说明读取期间发生新评或删除，前端刷新当前页并折叠历史，避免把另一条“当前点评”误放进历史。公开读取同样先核验父餐厅未删除。
- 主卡和历史的多SQL读取使用一致快照；账号名称通过user公开批量服务读取，照片关联通过review自有Mapper按本页点评批量读取，避免N+1。图片引用每条最多五个，列表不下载OSS字节；回复和全店照片墙后续单独分页或限量预览，不承诺无限内嵌。
- 主列表首步用有界页码分页，明确跨请求有新评时分组可能移动，不能承诺动态列表绝无重复/遗漏。单次查询计数及本页保持同一快照；本人发评后回第一页刷新。
- 公开GET可匿名，不依赖JWT显示删除按钮。正式删除阶段另提供认证管理能力，不能把用户名或请求中的authorId当权限。

### 5.3 本人计分上下文与预测（C步）

返回全店总条数、participantCount、精确评分累计值和本人currentReview（没有则null）。只允许查询当前登录人，不能传别人的ID；该上下文可由服务器作为预测读模型给出，不含数据库内部权限信息。

本人首次评价：分子加新分、分母加1；已有计分：分子减本人旧分再加新分、分母不变。推荐率同样替换。前端预测明确为估算，并发下不保证发布后完全一致；请求失败时不退回旧的“每条加一票”公式。

### 5.4 状态码与异常建议

| HTTP | 场景 |
| --- | --- |
| 400 | 非法ID、UUID、半分、正文、游标，或超量图片/不支持字段 |
| 401 | 未登录、无效或过期会话 |
| 403 | 后续管理接口越权；不能只靠前端隐藏按钮 |
| 404 | 餐厅不存在或已删除，公共场景不泄露删除内容；停业允许评价 |
| 409 | 幂等编号内容冲突 |
| 503 | 有界并发冲突重试耗尽或暂时依赖故障，前端保留正文与同次UUID |

错误响应不泄露SQL、内部表名、令牌或账号私密信息。具体机器码及示例在实施时同步docs/api.md。

## 6. 写入事务与并发

1. Controller只做协议和参数转换，作者来自CurrentActorService。规范化内容，按固定字段顺序计算SHA-256，摘要含餐厅ID与协议版本，不含易变展示名。
2. 通过restaurant公开服务SELECT FOR UPDATE锁父餐厅，验证可见性；所有点评发布/后续删除和现有餐厅删除共用父锁，先锁父再处理子资源。
3. 在锁定后核对同账号UUID。已存在时比较hash及完整规范化字段；相同返回原ID，不改变updated_at和统计；不同返回冲突。跨店同UUID竞争由已有数据库唯一键兜底。
4. 读取该账号旧代表，插入新点评并确认新代表。总条数+1；首次人数+1，老用户人数不变；各评分sum和推荐数按新旧代表作差量更新。
5. 统计更新经restaurant公开服务参与同一事务；新建餐厅同事务建零统计，旧数据缺行受控补齐。任一步失败，点评和统计一起回滚。
6. 遇到跨店同UUID唯一键竞争，必须先退出/回滚失败事务，再在新事务读取胜出记录、校验请求；不在可能已标rollback-only的事务里吞异常继续返回成功。实现采用最多3次独立READ_COMMITTED事务、每次事务超时10秒；在事务外重试并发锁/查询超时或唯一键竞争。死锁/锁等待有界重试整个事务，同UUID不变。
7. 事务提交后才返回成功；前端清除草稿、刷新分组、本人上下文和餐厅缓存。若提交成功但响应丢失，重试仍返回原ID，不生成第二条点评。

选择父店行锁的原因：复用已有删店互斥边界，单店操作有确定顺序，能直接证明评分一致。代价是热门店写入串行，因此锁内不做OSS/网络调用、邮件或逐作者外部查询；后续用锁等待和延迟数据判断是否需要更细粒度方案。

维护独立的统计重建服务：review只从自有表挑每人的代表并聚合，经restaurant公开服务写回；仍取得相同父锁，不能让重建覆盖并发新评。日常写入用差量，测试通过重建结果核对不变量。

## 7. 删除、图片与回复的后续衔接

2026-10-29顺序调整：先推进图片，不等待B/C。现已实现上传/即时取消/回收、有序photoIds绑定、正式图片访问及前端；写评期间本地预览。空图保持旧文本摘要，附图使用photo-review-v2。V6区分UPLOADING与PENDING_DELETE；云调用移出数据库事务，绑定以MANDATORY加入点评事务。V7支持五图；开发Bucket已完成真实上传/读取/取消独立验收，本地开发库已升级V7并加载新后端。浏览器正向持久化发布/阅读仍需随B3联调，不将独立OSS或替身验证称为完整页面验收。

- 删除历史：总条数-1，人数和累计分不变；删除代表且仍有历史：替换为上一条，人次不变；最后一条删除：人数-1，减去其代表分。本人/管理员权限必须服务端判断。
- V4幂等键随评价硬删除消失，不能承诺删除后重放旧UUID仍永久幂等。开放删除接口之前，必须补独立发布请求记录/删除回执及明确保留期限，使已删除请求不会被重放复活；结构及保留策略在删除阶段单独评审，首步不开放DELETE绕过这个问题。
- 图片阶段先实现媒体上传，再以已验证fileId发布；先落可重试的数据库清理状态，再处理OSS删除。使用版本化hash规范，新增图片字段后不破坏已发布文本请求的重试。
