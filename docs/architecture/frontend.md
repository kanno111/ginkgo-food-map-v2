# 前端架构

## 微信小程序端（2026-11-11）

小程序位于 `miniprogram/`，使用微信原生 WXML/WXSS/TypeScript，不引入 uni-app 或 Taro，也不复用 Vue 组件。它与 Web 端共享同一套后端 HTTP 契约，但与 Web 代码完全隔离，单独通过微信开发者工具编译。

```text
miniprogram/
├── app.ts / app.json / app.wxss   启动入口、路由表与全局视觉变量
├── assets/                        TabBar 图标与地图标记
├── custom-tab-bar/                悬浮玻璃底部导航
├── config/                        环境地址与相对图片地址拼接
├── typings/                       当前代码实际使用的微信 API 最小类型声明
├── shared/                        请求层、登录态存储、图片处理与格式化工具
├── modules/                       按业务域划分的接口与展示模型（含地图点位）
└── pages/                         找店、地图、消息、我的、我的内容、登录、店铺详情、写点评、新店投稿与资料纠错、公开主页与关注名单
```

- 视觉采用半透明玻璃层、环境色光斑、高光描边和悬浮胶囊导航；页面正文位于环境光之上，玻璃面板在支持 `backdrop-filter` 的环境启用真实模糊，不支持时退回半透明背景与内阴影。原生 TabBar 无法模糊，因此使用 `custom-tab-bar`，四个 Tab 页在 `onShow` 回写选中项。
- 请求层显式区分 `none`、`required`、`auto` 三种认证模式：公开读取不携带令牌，私有请求无令牌时本地拒绝；401 只清理产生该次失败的令牌。
- 登录只接受注册邮箱和密码，登录字段适配后端现有的 `username` 参数；不请求微信 openid、头像、昵称或手机号。登录态只保存后端会话和公开身份，不保存密码；页面在 `onShow` 重新读取，退出后不会沿用内存旧值。
- 注册与找回密码共用验证码倒计时：发送后 60 秒内禁止重发，页面卸载停止计时；验证码、密码与确认密码只存在页面内存。注册使用 `redirectTo` 替换登录页，成功后复用 auth 模块统一的 `finishAuthNavigation` 回到发起页；重置密码成功后清理本地会话并返回登录页，邮箱通过查询参数预填，不自动登录。
- 列表与详情使用请求序号丢弃迟到响应，避免快速切换筛选后旧结果覆盖新结果；点评响应在进入页面前校验关键字段与图片地址。
- 地图使用 GCJ-02 坐标：优先读取当前定位，拒绝授权时退回校园中心；用户拖动或缩放结束后节流读取视口四边，点位固定最多 100 条，截断时提示放大地图。标记编号与当次响应数组下标绑定，每次整体替换，避免旧标记跳错店铺。
- 消息中心复用本人收件箱接口，按 ALL/SYSTEM/COMMENTS/LIKES/FOLLOWERS 分类读取；列表、分类计数、各类未读数和最新系统摘要取自服务端同一快照，浏览不自动已读。公告以 `announcement:{id}` 作为列表键，回复详情通过本人回复定位接口重新鉴权读取，通知本身不保存正文，也不执行任意跳转地址。未读红点由消息页按快照回写，其他 Tab 页进入时轻量查询未读数。
- 写点评入口固定在普通餐厅详情和独立窗口详情，评价对象由页面带入，提交前不能换对象；食堂主体不接收点评，需先进入窗口。评分使用 0–10、步进 0.5 的滑杆；正文按去首尾空白后的码点计 5–500。照片先读取宽高限制最长边 1200px，再逐级压缩到 300KiB 以内，随后以 `purpose=REVIEW` 上传换取 fileId；失败照片按稳定 key 单独重试或移除，未全部成功时禁止提交。发布沿用后端 `clientRequestId`：内容不变的重试复用原编号，评分、正文或图片变化后换新编号；内容指纹包含目标类型，餐厅与窗口即使编号相同也不共用请求号。餐厅走 `/api/restaurants/{id}/reviews`，窗口走 `/api/canteen-windows/{id}/reviews`，回执必须回指同一类型和编号且另一身份为空，避免发布到同号对象。发布成功返回详情页并重读点评与评分。
- 详情页互动按点评和回复分别批量读取点赞状态，同一页最多 8 条点评，一次请求即可；状态缺失时保持“未知”，不补 0 也不显示未点赞。点赞写入以服务端回执更新计数，不在本地自增；401 只切换页面登录态，已读取的公开点评仍可阅读。
- 回复按游标分页展开，首次进入读取第一页，更多回复原样带回 `nextCursor`，不在前端构造分页位置。发布回复使用按点评缓存的请求号，正文变化后立即丢弃；删除本人回复需二次确认，服务端仍会按归属校验。举报面板在点击时固定目标类型与编号，原因使用固定枚举，说明按码点限制 200；本人内容在本地隐藏入口，服务端再次拒绝自举报。
- 我的点评与收藏共用一个受保护页面，通过 `tab` 参数决定首屏分类。点评读取 `/api/me/reviews` 的店铺分组，只展示本人当前有效点评；收藏读取 `/api/me/favorites` 并保留失效店铺占位，失效项不能打开详情但仍可取消收藏。切换分类、下拉刷新和追加分页统一用请求序号丢弃迟到响应；取消收藏失败只在列表上方提示，成功后按剩余条数回到仍有内容的页码。
- 新店投稿从找店页“添加店铺”进入，未登录时只展示登录卡片，不渲染可编辑表单，避免登录跳转丢失草稿。表单字段与后端 `POST /api/restaurant-submissions` 白名单一致：店名、普通餐厅/食堂、分类、人均类型与金额、地址、GCJ-02 坐标、营业状态、堂食/外卖三态、标签和最多 5 张照片；食堂显式提交空分类，未知人均提交 `null`。位置通过 `wx.chooseLocation` 选择并记录 `locationConfirmed`，已填写地址不会被地图结果覆盖。标签按行拆分，名称、坐标、金额、标签总长和图片编号在本地先校验，最终分类启用、图片用途和重复投稿仍由服务端判定。成功只代表待审申请已受理，页面跳转到“我的投稿”查看进度，不把申请编号当作餐厅编号打开详情。提交使用与点评相同的内容指纹与 `clientRequestId`：内容不变重试复用原编号，字段或图片变化后换新编号。
- 资料纠错复用投稿页并通过 `id` 参数进入：先读取公开店铺详情回填名称、类型、分类、人均、地址、坐标、营业状态、堂食/外卖和标签，再提交完整快照到 `POST /api/restaurants/{id}/change-requests`。历史坐标只用于回填，仍要求用户主动确认或重新选点；已有公开照片不进入 `photoIds`，只提交本次新增图片。资料未成功读取时禁止提交，避免用不完整表单覆盖未展示字段；失败重试沿用同一 `clientRequestId`，内容或目标变化后换号。独立食堂窗口不显示该入口。
- 图片压缩与临时图上传由 `shared/lib/image` 和 `shared/api/files` 提供，点评与投稿共用最长边 1200px、300KiB 的压缩规则，但分别使用 `REVIEW` 与 `RESTAURANT` 上传用途，不能混用图片绑定关系。
- 投稿与纠错记录包含列表与详情：列表按服务端状态计数筛选并分页，详情展示原提交与审核通过快照、驳回原因和 0–4 位置附图。附图是私有资源，`<image>` 无法携带认证头，因此先用 Bearer 下载到临时文件再展示，失败按图重试。待审申请可进入修改或确认撤回，被驳回申请可修改后重新提交；修改走 `PUT /api/me/restaurant-requests/{id}`，重提走 `POST /api/me/restaurant-requests/{id}/resubmit` 并生成新申请。详情接口不暴露原附图文件编号，表单必须说明需要重新选择上传；服务端仍会复核申请状态和归属。目标店铺被删除时保留申请快照但不提供跳转，UPDATE 申请也不再提供重提。
- 公开主页以用户编号进入，登录后读取白名单资料、关注人数与关注状态；点评与收藏分别读取 `/api/users/{id}/reviews` 和 `/api/users/{id}/favorites`。收藏 403 时明确显示“私密”，不降级为空列表；关注/粉丝名单由独立页面读取，403 时原样提示私密。关注写入使用 PUT/DELETE 表达目标状态，回执必须回指同一用户且最终状态与请求一致，未确认时重新读取而非乐观更新。自己的主页隐藏关注按钮，自己的关注名单提供取消关注；“我的”展示本人关注/粉丝人数，点评作者与新增关注消息均可进入公开主页。
- 成长页只读取本人成长摘要，等级、经验与门槛完全使用服务端值，不由前端按经验推算；最高级以 `nextLevelThreshold=null` 处理。
- 资料页只读取本人白名单资料，完整邮箱不进入前端缓存；简介草稿只保存在页面内存，退出、换号或重新加载即丢弃。前端按码点计数并做 100 字上限提示，规范化、控制字符与联系方式检查仍以服务端为准；保存回执必须与本页用户一致，失败保留草稿。
- 隐私设置读取收藏可见性与关注/粉丝名单可见性两套接口：收藏单独提交，关注与粉丝共用一次完整提交，不能只写被切换的一项。保存期间禁用全部开关，避免并发写入产生非预期组合；失败时先恢复到上次确认值，再重新读取服务端设置，不把未确认状态当作成功。进入页面与从登录返回时都重新读取，避免沿用其他设备已修改的设置。
- 独立窗口复用店铺详情页并通过 `windowId` 分支：资料与相册读取 canteen-windows 接口，点评、回复、点赞、举报继续以点评编号为入口。窗口推荐率在接口中是 0–100 百分数，进入展示模型前换算为比例；相册最多 5 张，读取失败只提示相册不可用，不阻止资料与点评展示。窗口没有收藏，收藏按钮与请求均被跳过；写点评通过 `windowId` 进入编辑页并发布到窗口接口，不能复用同号的 `id` 参数。消息回复若指向窗口，跳转参数改用 `windowId`，本人点评分组也按 `targetType` 选择窗口或餐厅详情。
- 普通用户侧尚未接入贡献榜与独立点评照片墙；管理端页面保持网页专属，小程序不提供管理员操作入口。

## 食堂窗口

普通餐厅沿用restaurants路由；窗口使用`/canteen-windows/:id`，同号对象通过类型隔离。restaurantApi在食堂详情读取完整窗口集合，canteenWindowApi将独立窗口协议转换为展示模型；详情和列表评分使用后端统计。窗口不包含餐厅分类，只按楼层筛选；窗口详情及管理页均无分类展示或输入。ReviewPanel、ReviewHistory、ReviewComposer及消息定位均显式传递窗口类型，个人点评的分组键包含类型。

`/admin/restaurants/:id/windows`复用商户工作台布局，通过管理员接口维护真实窗口。读取失败可重试，写入成功但读取失败只重新GET；创建结果未知时冻结原内容和UUID重试确认。换号清除资料并忽略迟到回执，页面卸载取消读取，写入期间阻止路由离开。接口与未开放范围见[API 22](../api.md#22-食堂窗口资料点评与汇总)。

WindowPhotoManagement为已保存窗口提供独立照片管理，压缩后以WINDOW用途上传，入册超时保留原fileId重试，不重复上传；换号或卸载忽略迟到响应并清理未绑定文件。窗口集合消费coverUrl，WindowAlbum独立读取窗口相册，提供缩略图、大图及读取/单图失败重试，不用点评照片补空相册。照片操作即时保存，首张为封面，每窗口最多5张。

## 社区页面与身份隔离（2026-11-07）

“我的点评”由review公开导出MyReviews，account只装配组件。本人列表使用独立私有接口，不遍历全站商户或把公开点评页过滤成个人列表。历史与删除复用现有点评组件及Gateway；读取代次、会话上下文与固定凭证共同阻止旧GET/DELETE回执影响新账号。删除成功与刷新失败分别展示，读取重试不再次删除，取消/卸载不在前端修改评分或经验。接口边界见[API 10.5](../api.md#105-本人点评按店铺分组)。

“我的投稿 / 纠错”由restaurant公开导出MyContributions，account只装配。myRestaurantRequestsApi独立消费本人白名单协议，不复用管理员详情或队列；校验返回userId、申请ID、分页和状态，丢弃未知字段，图片地址由固定本站路径生成。useMyRestaurantRequests分离列表/详情代次及会话上下文，固定请求凭证；状态切换回第一页，失败重试原请求页码，读取故障不伪装为空记录。只在打开详情后请求最多五张私有附图，每张独立重试，关闭/切换申请、退出、换号及卸载中止旧请求、释放Blob URL，迟到响应不能创建旧图片。详情用原生dialog，审核通过内容与原提交分别按纯文本展示，不提供审核操作；待审修改、撤回和驳回重提的后端接口已提供，前端入口尚未接入。接口见[API 16](../api.md#16-本人投稿与纠错记录)。

account模块拥有个人中心、公开主页壳、设置、本人成长读取及本人资料编辑；pages/account只通过公开index装配组件。community模块通过公开index提供UserIdentity和ContentActions，供点评与回复共用用户名跳转、待开放互动入口，避免把业务身份放入shared。消息分类继续由message模块维护。

useOwnGrowth固定发起时令牌、绑定当前用户ID，取消及代次校验防止换号或卸载后的旧结果覆盖新页面；接口失败不回退为零经验。公开他人主页不读取本人成长接口、不复用本人资料，游客不挂载个人内容。未知互动人数及未接通列表不以0或空数组冒充真实结果。

useOwnProfile只在本人个人中心、本人主页或设置启用，使用页面内存保存服务端白名单资料；接口只返回脱敏邮箱，前端不缓存完整邮箱。请求固定令牌和用户ID，通过会话上下文、读取代次及AbortController隔离迟到结果；保存前使旧GET失效，防止读取旧简介覆盖新回执。服务端userId必须匹配当前用户，PATCH回执简介必须匹配本次规范化内容才确认保存。切换账号、令牌或离开页面清理快照和请求，访问他人主页不复用本人字段。

简介编辑器按Unicode码点计数并做基础联系方式检查，服务端仍是最终校验来源。失败保留本次草稿；取消、退出或换号清除，不写浏览器存储。保存中阻止重复提交及Esc/取消关闭；请求取消不代表服务器事务撤销，重试以完整简介覆盖，契约见[API 15](../api.md#15-本人资料与简介)。隐私、收藏仍等待真实接口；审核/评论通知与已读已接通，消息只保存来源，评论点击后由review模块重新鉴权读取原点评和目标回复。举报弹窗按点击挂载并Teleport到body，避免常驻隐藏表单干扰回复编辑。登录回跳由auth内白名单统一校验，既有管理员角色分流继续优先。具体页面与待办见[社区前端状态](../plans/community-frontend.md)。

## 管理端身份与布局（2026-11-03）

统一使用`/login`和auth模块的LoginForm，经既有`/auth/login`建立会话；旧`/admin/login`仅兼容跳转。login.store.isAdministrator根据服务端身份的`ROLE_ADMIN`计算，管理员优先于普通回跳进入工作台，普通用户保留安全站内回跳。DefaultLayout在身份恢复前隔离内容，管理账号访问前台路由也进入工作台，管理员日常使用普通账号需先退出。

AdminLayout在会话恢复后通过admin模块公开的verifyAdminSession调用`GET /api/admin/me`，验证成功才挂载工作台。后端按当前数据库角色限制`/api/admin/**`，并保留JWT和Redis验证；前端403拒绝访问、503显示重试、401清理会话。管理校验固定绑定请求开始时的凭证，凭证切换或布局卸载后丢弃旧结果。App统一负责恢复与跨标签页凭证同步，不新增第二套登录存储。

AdminReviewPage从auth模块取得真实身份及退出行为，以props/events传入admin模块，admin模块不读取auth内部Store。认证失效时销毁审核组件及其内存状态。后台品牌不链接前台，提供退出以切换普通账号。

useRestaurantRequests读取真实申请分页、详情和私有图片，维护当前申请独立草稿并调用真实通过/驳回接口。ReviewInlineField按字段类型处理文字、数字、枚举和标签，只有维护协议白名单进入通过请求，不提交展示文案和原始申请身份。状态/搜索/翻页清除旧详情，搜索防抖250ms；固定请求凭证，取消与版本号隔离迟到响应。提交期间锁住切换和重复写入，网络失败保留草稿；收到终态回执后读取服务端审核快照并刷新队列，查询失败不能被视为审核失败。连续审核选中刷新后下一条，取消勾选保留回执，队列缩页沿用此策略。图片经Bearer取得Blob，切换/卸载撤销URL，原申请图片不自动变为公开相册。

审核白名单使用独立协议，包含restaurantType、supportsDineIn、supportsDelivery，不再照搬基础直接维护输入而漏掉这三个字段。类型使用普通餐厅/食堂选择；堂食与外卖使用未知/null、支持/true、不支持/false，草稿编辑、提交、服务端快照和公开详情保持一致。

## 正式商户相册

RestaurantDetail使用restaurant模块自己的RestaurantAlbum，不再将ReviewPanel当前点评页的photos事件作为顶部图片源；点评照片保留在点评区。普通餐厅与食堂共用正式相册组件，评分刷新不会重新挂载相册。桌面保留左图右资料，手机统一先资料后相册。

restaurantAlbumApi按20张请求有界游标分页，投影id/position/cover，图片地址由商户ID和正式关联ID生成，不使用外部图片URL。httpClient仅对明确的公开相册GET省略Bearer，管理员原申请图片仍携带认证；避免过期令牌阻止公开图片浏览。

useRestaurantAlbum使用独立代次、AbortController和四并发工作池加载JPEG Blob；封面先加载，点击仍在队列的缩略图会优先处理。分页失败保留已加载内容和当前选择，元数据空态、查询失败和单图失败分别展示；解码错误可单图重试，切店/卸载撤销全部ObjectURL，迟到响应不创建旧图片URL。RestaurantAlbum提供缩略图、大图原生dialog和Esc关闭，不用未审核图、点评图或样例图补空相册。

管理端按publishedPhotos显示本次发布数量和正式链接；已删除目标保留发布记录但不提供公开链接，历史已通过且无正式关联时明确未发布。通过回执按真实发布数量反馈，原photos继续通过管理员私有接口核对。没有增加图片发布写接口或修改后端审核规则。

首页RestaurantCard和地图MapRestaurantPhoto消费目录/详情返回的coverPhoto，停止调用useRestaurantReviewPreview逐商户拉取点评。封面URL按商户和正式关联ID生成，原卡片布局、懒加载、图片失败占位保留；后端分页后仅以当前页ID集合批量查询position=0的有效正式关联，不遍历相册或在目录排序/计数中加载图片。无正式封面保持null，不回退为点评照片。餐厅类型优先使用明确restaurantType，旧数据缺省时才兼容食堂分类。

RestaurantCorrection在已有商户资料加载成功后复用RestaurantAlbum回显公开照片，使用源商户名称，编辑店名不会把旧相册署名改成尚未通过的新名称。相册状态与useDraftPhotos的新增上传草稿分离，不进入dirty基线、五张新增限制、取消清理或提交photoIds；认证变更/切店/提交成功卸载相册时正常撤销Blob。新店投稿不挂载现有相册，读图失败独立重试且不阻止文字提交。

## 账号交互（2026-11-01）

注册调用/register-and-login并通过login.store.acceptSession接收正式会话后进入首页；令牌与公开身份沿用现有认证状态，密码不进入Store。请求期间出现更新的登录时不覆盖该新会话。密码重置调用/password-reset，成功清理请求开始时的旧令牌，通过loginPrefill模块内存一次性传递服务端返回的用户名，跳转/login；登录密码为空，不自动发送登录请求、不在URL或持久存储传递用户名/密码。字段规则集中于accountValidation，失焦/提交显示框下提示。

## 源码分层

```text
src/
├── app/                 应用启动后的顶层装配、布局和路由
├── pages/               路由页面，只编排模块，不实现底层业务
├── modules/             按业务域组织的功能模块
│   └── system/
│       ├── api/         当前模块的后端调用
│       ├── model/       类型、Pinia Store 和业务状态
│       ├── ui/          当前模块专属组件
│       └── index.ts     模块对外公开入口
├── shared/              不含具体业务语义的公共能力
│   ├── api/             HTTP 基础设施与通用协议类型
│   ├── lib/             无副作用工具函数
│   ├── styles/          全局样式和设计变量
│   └── ui/              跨业务复用的展示组件
└── main.ts              唯一浏览器启动入口
```

## 依赖方向

```text
main -> app -> pages -> modules -> shared
```

- 依赖只能向右，禁止反向依赖。
- `shared` 不得引用任何业务模块。
- 页面通过模块的 `index.ts` 使用公开能力，不直接读取模块内部 API 或 Store。
- 一个模块不能直接读取另一个模块的 Store；跨模块协作通过公开函数或页面编排完成。
- API DTO、表单模型和页面展示模型按用途分开，不能直接把后端实体当作任意组件的状态对象。
- 只有确实跨模块复用的代码才能进入 `shared`，不能把它当作杂物目录。

认证模块统一提供登录表单和账号状态。`app` 布局负责将账号状态传入公共导航展示组件，
公共导航通过事件通知布局执行退出或重试，不直接依赖认证模块。
HTTP 基础设施只负责当前标签页的 Bearer 凭证读写和401清理；503保留凭证供重试，
过期旧请求的401不得清除新登录的凭证。密码仅留在表单局部状态，不进入 Pinia 或浏览器存储。

ESLint 已对主要反向依赖进行静态限制。新增 `restaurant`、`review`、`auth` 或 `admin` 功能时，应在 `modules` 下建立独立目录，并保持相同的内部职责划分。

## 公告管理与用户阅读

announcement模块通过公开index导出公告API白名单与AnnouncementReader，admin拥有发布表单及记录状态模型；pages/admin/AdminAnnouncementPage只装配当前身份和工作台。`/admin/announcements`继续由AdminLayout和真实管理接口授权。发布页面遵循确认的单列示意图，不含预览或独立说明区域，固定全体用户，记录页支持状态筛选、分页、重新读取详情及撤回。

useAdminAnnouncements绑定账号/凭证及读取代次，取消旧请求并拒绝迟到结果。一次发布尝试冻结UUID及正文，未知结果保持原请求重试；成功后清空草稿进入记录，列表故障不再次发布。提交中禁止重复写入及离开，身份变化清理草稿、确认和回执，不写浏览器存储。

message的收件箱校验ANNOUNCEMENT与announcement:ID的一致性，标题不冒用审核店名，详情通过用户接口读取。AnnouncementReader采用原生dialog和纯文本插值，退出/换号/卸载取消读取；SSE变化和重连使当前收件箱及打开的公告重新核对，撤回后先清除旧正文，再显示不可访问。写操作期间合并刷新提示，操作结束再重读，避免实时事件打断已读或删除回执。
