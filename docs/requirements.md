## 2. 产品目标、用户与范围

### 2.1 产品定位

面向电子科技大学学生，以 Ginkgo 烹饪社为起点，服务成都校园及周边觅食场景。用户通过地图和餐厅列表发现店铺，通过真实体验评价判断是否值得去，并补充新的店铺信息。

核心体验保留原版的五档杯型、四维评分、地图与列表联动、评价和照片。评分来自有效评价计算，管理员不能直接修改综合分或指定杯型。

视觉迁移约束（2026-10-28 用户明确要求）：沿用原版封面、杯型图形、配色与相关标语，优化布局和操作效率时不得自行替换品牌素材或改写口号。当前前端步骤已恢复原版 `template.html` 的页头杯子、兔子封面与首页文案、`app.js` 的 `cupGlyph`/文字前景规则，以及 `core.js` 中的杯型颜色和标语。全家桶红色 `#C0392B` 配金色 `#E9B949` 描边，超大杯 `#B5651D`、大杯 `#C98A4B`、中杯 `#D8B98A`、小杯 `#8A94A6`、待评级 `#B9B2A4`；中杯和待评级为深色文字，其他为白色。地图尚未接入，后续地图标记也须对照原版，不用杯型徽章冒充已实现的地图。

手机验收补充：首屏压缩封面区；搜索保持可见，其他条件可展开/收起，折叠不清空筛选且显示已选项数；目录按钮和排序控件至少44像素高；杯型可横向滑动但整页不能横向溢出；翻页返回结果区，浏览器后退恢复目录阅读位置。当前候选数量、结果数和分页来自同一集合，不照搬原站的实时统计数字。真实地图聚合、城市范围选择、地图与列表联动及真实数据接入仍属于后续步骤。

### 2.2 核心使用场景

1. 不知道吃什么：按名称、地址、分类或标签找店，结合人均、评分、评价数和距离做决定。
2. 想了解一家店：打开详情，看四维均分、推荐率、评价正文、照片及近期补充信息。
3. 吃完分享：登录后给出四维评分、推荐判断和正文，提交后刷新店铺评分。
4. 发现新店或信息错误：新增餐厅，维护自己创建的餐厅，向运营人员反馈他人店铺的信息问题。
5. 运营维护：处理违规内容、恢复误删内容、导入收集表和备份业务数据。
6. 更换设备：登录同一账号后继续管理自己的内容，解决原版权限跟设备走的问题。

### 2.3 本轮重构的边界

- 优先完成“查找餐厅 → 查看详情 → 发布真实评价 → 更新评分 → 管理自己的内容”的闭环。
- 使用已有账号和权限体系替换共享社团口令、共享管理员口令和设备 ID 归属判断。
- 服务端和 MySQL 是共享数据的权威来源；不迁移浏览器全量业务数据 upsert 的写入方式。
- 本文只建立后续需求与顺序，本次不直接实现业务代码、执行数据迁移或调整生产服务。
- 下单、支付、配送、商家入驻、广告投放、商业推荐位、小程序和原生 App 不纳入当前重构。

## 4. 角色与权限

### 4.1 角色定义

- 访客：未登录，可以阅读餐厅目录和详情，不能新增餐厅或发布评价，D01已由用户确认。其他公开内容按对应阶段确定字段及可见集合。
- 普通用户：已验证校园邮箱且账号可用，使用 `ROLE_USER`，可以新增内容并管理自己的资源。
- 管理员：通过独立授权获得 `ROLE_ADMIN`；除普通能力外，按权限处理内容、管理数据和查看管理记录。
- 系统任务：执行统计重建、临时图片清理或备份，使用明确任务范围，不模拟普通用户账号。

### 4.2 权限矩阵（V2 建议基线）

| 操作 | 访客 | 普通用户 | 管理员 |
| --- | --- | --- | --- |
| 看公开餐厅目录、详情、评分说明 | 允许，D01已确认 | 允许 | 允许 |
| 看公开评价、地图、榜单 | 建议允许，随对应功能细化公开范围 | 允许 | 允许 |
| 新增餐厅、发布评价、回复 | 不允许 | 允许 | 允许 |
| 编辑餐厅 | 不允许 | 仅自己创建的 | 按管理权限允许 |
| 删除餐厅 | 不允许 | 仅自己创建的，须确认影响 | 允许 |
| 编辑评价（新增需求） | 不允许 | 仅自己的 | 默认不替作者改正文或分数 |
| 删除评价、回复 | 不允许 | 仅自己的 | 按管理权限允许 |
| 恢复已删除内容 | 不允许 | 初期不提供自助恢复 | 允许，需检查父资源状态 |
| 收藏及个人内容列表 | 不允许 | 仅自己的 | 不因此获得他人私有列表访问权 |
| 导入、全量导出、永久清理 | 不允许 | 不允许 | 独立管理权限 |
| 授予管理权限、改系统配置 | 不允许 | 不允许 | 需另行限定的高级管理权限 |

所有修改操作由服务端从当前身份确定 `userId`。请求中伪造作者、创建者、角色、历史设备 ID 或客户端按钮状态，均不能取得权限。停用账号即使持有旧 JWT 也不得写入。

### 4.3 运营与审核策略

原版主要是发布后管理员删除，没有完整的发布前审批流程。建议初期采用“校园账号直接发布 + 频率限制 + 管理员事后处理”；是否引入待审核、驳回、申诉等状态，见 D03。不得将尚未实现的自动审核或举报处理描述为现有能力。

## 6. 餐厅需求

### REST-01：阅读、搜索、筛选和排序（原版迁移，P1）

依据：S02 的 `visibleRestaurants`、`sortRestaurants`、`cardHtml`、`renderDrawer`。

**功能规则**

1. 卡片显示名称、分类、人均、地址摘要、标签、综合分、杯型、评价数、距清水河校区的直线距离；未知值明确显示“待补充”，不伪造分数和距离。
2. 搜索范围包含店名、地址、分类和标签；去除查询首尾空白，支持中文和常见大小写差异。空搜索返回默认列表。
3. 杯型支持五档与“待评级”，允许组合筛选；列表胶囊与地图图例共享筛选条件。
4. 保留“全部 / 只看推荐 / 只看踩雷”视图：原版“推荐”指大杯及以上，即评分至少 6.2，不是推荐率阈值；“踩雷”只指小杯，不包括待评级。
5. 支持综合分、四个维度、评价数降序，以及人均升序。无分数、人均未知排在对应有效值之后；同值按名称、稳定 ID 排序，保证分页顺序稳定。
6. 原版停业店铺仍有记录并显示停业提示；V2 建议允许查看并提供隐藏停业筛选。是否进入榜单单独处理。
7. 服务端分页返回记录、总数与分页信息。当前后端实现暂沿用现有页面每页8条，单次上限100条；原建议默认20条与最终分页产品参数仍待审核，不据此扩展为其他决策已批准。
8. 详情显示四维均分与图形、推荐率、有效评价数、评价列表和照片墙。评价列表建议按发布时间倒序分页；图片和回复按阶段接入。

**验收标准**

- 新建无评价店铺显示“待评级”和 0 条评价，评分与推荐率不显示为 0 分/0%。
- 相同关键词与筛选条件下，列表、地图、总数和榜单使用明确一致的口径，不把列表当前页当成全部餐厅。
- “推荐”视图不包含 6.19 分、待评级或小杯店铺；“踩雷”不包含无评价店铺。
- 删除店铺不进入普通列表、搜索、详情和地图；接口直接访问也不能泄露回收站内容。
- 评价明细分页不影响店铺总评分，评分必须依据全部有效评价。

### REST-02：新增、编辑和补充位置（原版迁移 + 权限调整，P1）

依据：S02 的 `openRestaurantModal`、`submitRestaurant`、`normalizeRestaurant`。

同名不同分店允许存在。同名同址或同一地点标识应提示疑似重复，不能只按店名覆盖现有店铺。普通用户初期只能修改自己创建的店，管理员可以纠错；“所有人协作编辑”不自动沿用。

**验收标准**

- 保存成功后，刷新与另一设备读取到相同数据；保存失败不提示成功。
- 修改请求不能改变创建者或综合分，也不能将普通用户伪装为管理员。
- 用户 A 无法通过改请求 ID 修改用户 B 的店；管理员授权单独验证。
- 两人从同一份资料开始保存时，允许依次成功，最终为最后成功保存的完整资料及标签，不混合两次标签内容。
- 搜索只定位到道路时，不能把路名自动当成店名；坐标未确认时给出明确提示。

**当前实现进展（2026-10-28）**：新增、完整编辑、经营状态及标签替换、私有管理资料已实现。用户随后明确取消餐厅版本号，编辑/删除/恢复不再要求或返回版本，不比较或递增餐厅版本列；保留当前认证身份、数据库实时管理员角色、主行锁、当前删除状态及事务。Unicode长度、人均整数/空值、确认坐标、启用分类、标签同库排序规则去重及总码点数80已校验。未知JSON字段拒绝；来源/创建者不允许改写。前端新增/编辑表单已接入真实接口，填入管理快照并提交完整替换，保留现有停用分类；手动GCJ-02输入及二次确认、不自动填坐标。失败保留输入，账号变化锁住原草稿，不自动重试POST。同名同址提示、频率限制、内容审核及评价关联治理仍未实现。

### REST-03：停业、删除与恢复（原版迁移，P1）

1. 停业只改变经营状态，仍可查历史信息；是否允许对停业店新增评价，见 D07。
2. 删除默认是软删除，记录操作人、时间与原因类型；删除前提示关联评价数量。
3. 删除餐厅后，其评价、回复与照片不对普通用户显示，但不直接抹除子记录，保留恢复能力。
4. 恢复餐厅不应恢复此前独立删除的评价或回复；只重新展示仍有效的子内容并重算统计。
5. 普通用户只能删除自己创建的餐厅；是否限制“已有其他人评价的店铺”由创建者自删，见 D02。
6. 只有管理员进入回收站并恢复；餐厅恢复核对当前账号权限和删除状态，不要求版本号；后续子资源恢复另行核对父子关系。

**验收标准**：删除后各入口一致隐藏；恢复后不丢失仍有效评价；独立删除的子评价不复活；停业与删除互不混淆；重复删除/恢复有稳定结果且不重复计分。

**当前实现进展（2026-10-28）**：软删除及管理员按ID恢复已实现，均无需版本号，保留标签、来源和创建者；删除后公开读取隐藏，恢复清空当前删除信息。重复操作返回明确404/409且不重复修改删除元数据。详情已接入服务端授权后的编辑/删除入口，删除二次确认显示名称、当前评价数量及影响；成功才离开详情并使目录缓存失效，返回时校正有效页码，失败不显示成功。当前无评价/回复/图片模块，D02中“有他人评价后能否自删”仍待后续确定；回收站分页与页面、治理审计及子资源恢复不能据此标为完成。

## 7. 地图与地点检索

### MAP-01：地图阅读与列表联动（原版迁移，P1）

依据：S02 的 `MapCtl`、`markerSvg`、`distanceText`、`locateUser`。

- 默认展示成都视野，清水河校区作为校区距离参考点；“距校区”是直线距离，不是步行距离或距用户距离。
- 使用不同颜色、大小的杯型图标；待评级和停业有明确样式，选中店铺可辨识。
- 点击卡片或地图点位打开同一详情；选中状态与地图视角联动；缩放后适当展示店名。
- 支持放大、缩小、回到默认视野；定位需用户授权，浏览器位置与腾讯地图坐标应正确转换，避免重复转换。

### MAP-02：新增餐厅时的地点搜索（原版迁移，P1）

1. 明确区分“搜索本站已收录餐厅”和“搜索地图服务的地点”。
2. 保留联想 → 城市地点搜索 → 地址解析的降级体验；默认在成都市范围理解查询。
3. 单一、足够明确的结果可以自动采用；多个结果必须显示名称和地址供确认，不默认选错分店。

7. 地图服务不可用时给出具体反馈，可继续手填；不得把失败结果当作有效坐标保存。

## 8. 评价与评分

### REVIEW-01：发布评价（原版迁移，P1）

依据：S02 的 `renderReviewForm`、`submitReview`、`updateReviewPreview`。

- 仅允许已登录且账号可用的用户，对当前有效餐厅发布；停业店策略见 D07。
- 四个维度为味道、性价比、服务、环境，全部必填，0–10，步进 0.5；后端拒绝缺项、越界、非数值和非半分步长。
- 明确选择推荐或不推荐，与四维分数独立；不以推荐判断替换评分。
- 正文去除首尾空白后为 5–500 个 Unicode 字符；按纯文本处理，不执行 HTML。
- 作者来自当前账号，不再使用自由填写昵称证明归属；显示名与账号 ID 分离，不能伪造其他作者。
- 图片最多 2 张，按 FILE-01 分阶段接入。先完成无图评价时，页面应明确当前阶段不支持图片。
- 表单显示本条总分、店铺当前杯型与加入本条后的预测结果；预测仅供参考，提交后的服务端聚合值才是正式结果。
- 允许同一用户因不同用餐经历发表多条评价；是否改为一人一店一条，见 D04。防重复提交与刷屏策略不能只依赖禁用按钮。
- 失败保留可恢复的正文草稿；登录失效需引导重新登录并避免将 A 账号草稿自动提交到 B 账号。

**验收标准**

1. 直接调用接口也不能提交弱校验数据、伪造作者或关联已删除餐厅。
2. 相同提交重试不会因网络超时产生重复评价；最终去重或幂等策略在接口设计时明确。
3. 提交成功后，详情、卡片、地图杯型、排行榜使用同一有效评价集合。
4. 没有成功写入数据库时，不增加本地评价数或显示“已发布”。
5. 图片失败不得无提示地变成“仅文字发布成功”。

### REVIEW-02：修改自己的评价（V2 新增，P2）

- 作者可以修改四维分数、推荐判断、正文与图片；不能改变作者和所属餐厅。
- 保留原发布时间，显示修改时间；记录版本，避免覆盖另一设备刚保存的修改。
- 修改后重新计算统计；编辑预测必须先排除该评价旧值，再加入新值，不能当作新增算两次。
- 已删除、被管理处理或父餐厅不可用的评价不能绕过状态限制修改。
- 管理员默认使用隐藏/删除与恢复处理内容，不代作者改分或改写正文；若需要代编，另设显式权限和留痕规则。

**验收标准**：其他账号改请求 ID 仍被拒绝；修改不新增评价条数；旧图片解绑后不会误删其他评价图片；两个旧版本并发保存有明确冲突。

### REVIEW-03：删除、恢复与个人评价列表（原版迁移 + 账号化，P1）

- 作者可软删除自己的评价；管理员按管理权限删除任何评价并填写处理原因。
- 删除后该评价从评分、推荐率、榜单和公开详情中移除，回复及照片不可继续绕过父内容公开读取。
- 管理员恢复有效父餐厅下的评价后重新计分；父餐厅已删除时应先恢复餐厅或明确拒绝，不产生公开孤儿内容。
- 提供“我的评价”分页入口；同一账号跨设备能管理自己的评价，不再依赖设备 ID。
- 不向普通用户公开他人的回收站内容或管理原因。

**验收标准**：删除与恢复分别只变更一次计数；所有评价删完后回到待评级；无权用户无法恢复或删除；页面与服务端异常状态一致。

### SCORE-01：评分计算与杯型（原版迁移，P1，正确性 P0）

依据：S01 的 `overall`、`aggregate`、`tierOf`。以下口径须由后端统一实现，前端只做展示和非权威预测。

| 指标 | 计算规则 |
| --- | --- |
| 单条评价总分 | 四个维度算术平均，先按四舍五入保留 2 位小数，与原版保持一致 |
| 餐厅综合分 | 全部有效评价的单条总分再做算术平均；杯型判定前不截断或四舍五入 |
| 四维均分 | 分别对每个维度的全部有效分值求平均 |
| 推荐率 | 有效评价中“推荐”的条数 ÷ 有效评价总数 |
| 评价数 | 全部有效评价数量，不能用本次加载的当前页数量 |
| 无评价 | 综合分、维度均分、推荐率均为空，杯型为待评级，评价数为 0 |
| 展示精度 | 评分展示 1 位小数，推荐率展示整数百分比；不得用展示值反推杯型 |

| 杯型 | 原始综合分区间 |
| --- | --- |
| 全家桶 | 8.6 ≤ 分数 ≤ 10 |
| 超大杯 | 7.4 ≤ 分数 < 8.6 |
| 大杯 | 6.2 ≤ 分数 < 7.4 |
| 中杯 | 5.0 ≤ 分数 < 6.2 |
| 小杯 | 0 ≤ 分数 < 5.0 |
| 待评级 | 没有有效评价，不等同于小杯 |

有效评价至少满足：评价本身未删除、符合发布策略、父餐厅未对公众隐藏。测试/演示评价不得计入生产评分。账号被停用是否追溯移除历史正常评价，见 D05；建议保留正常历史内容，违规内容另行处理。

后端应使用明确的十进制精度与舍入规则；上述正数“四舍五入”按 `HALF_UP` 理解，避免二进制浮点误差或不同舍入模式导致杯型边界漂移。

**必须覆盖的验收样例**

- 原始综合分 8.599 为超大杯，8.600 才是全家桶；其余 7.4、6.2、5.0 边界同理。
- 8.5 与 8.6 两条评价的平均值为 8.55，展示可为 8.6，但杯型仍是超大杯。
- 四维为 8、8、8、7.5 时，单条平均 7.875，单条总分保存/计算口径为 7.88。
- 四维全 0 是有效的 0 分评价，不得当成缺失；四维全 10 得 10 分。
- 删除、恢复、修改、导入、撤回审核均触发正确更新，失败事务不留下半更新统计。
- 管理员不能通过修改餐厅请求直接提交 `score`、`tier`、`reviewCount` 来改变结果。

### SCORE-02：评分说明和社区规范（原版迁移，P1）

页面解释四维含义、0–10 分参考、杯型阈值、推荐率与杯型的区别，并提示评价数较少时可信度有限。保留真实体验、说明菜品/消费/等待时间、避免刷分、人身攻击、广告及隐私泄露等规范。不得将榜单描述为学校官方评价或商业认证。

## 9. 图片与文件

### FILE-01：上传、绑定和查看评价图片（原版迁移 + 存储调整，P1）

依据：S02 的 `compressImage`、`handlePhotoFiles`、`renderDrawer`、照片远端转换逻辑。

**使用规则**

1. 每条评价最多 2 张，支持选择文件；桌面拖拽上传作为保留体验。发布前可预览、移除，详情支持照片墙和大图查看。
2. 图片必须与成功发布的评价一起可跨设备读取；不再只存在浏览器 IndexedDB，也不将 base64 塞进业务表或 JSON 评价正文。
3. 前端压缩用于体验优化，建议最长边 1200px、目标单张 200KB；服务器独立校验实际类型、可解码性、尺寸与最终大小。
4. 初期建议允许 JPEG、PNG、WebP，拒绝 SVG、可执行内容和伪造扩展名；HEIC/动图是否转换，见 D08。原图上传上限、像素上限和服务端输出上限在文件接口设计时确认。
5. 不静默沿用旧版“图片超总量上限便只上传文字”。图片未就绪时，阻止整体发布并给出重试/移除选项；用户明确移除后才可只发文字。
6. 普通用户只能绑定自己上传、仍有效且用途正确的临时文件。不能传入他人文件 ID、任意公网 URL 或服务器路径来取得图片。
7. 文件保存随机标识、所属账号、媒体类型、尺寸、大小、存储位置、状态与关联信息；接口不暴露真实服务器路径。
8. 图片处理宜重新编码并去除不需要的 EXIF 位置信息。页面提示不要上传未经同意的人像和隐私信息。

**生命周期**

| 阶段 | 预期行为 |
| --- | --- |
| 临时上传 | 只归上传者使用；有明确过期策略，不立即成为任意用户可见的公开资源 |
| 评价发布 | 校验归属和数量后绑定；评价与文件关系不能半成功 |
| 评价修改 | 新文件绑定、旧文件解绑；是否立即删除物理文件由清理策略决定 |
| 内容软删除 | 普通公开访问同时受父内容状态约束，不能只靠隐藏图片按钮 |
| 内容恢复 | 保留期内图片可恢复，不能提前清理仍可恢复内容的文件 |
| 过期或永久清理 | 仅清理确认无有效引用的文件，支持失败重试，禁止误删其他内容图片 |

**验收标准**：伪造图片、超量、越权绑定均在服务端被拒绝；A 设备发布后 B 设备能看图；上传失败不报告整条评价成功；删除和恢复不出现失控的公开图片或悬空引用。

**存储方案待确认**：小规模可先使用持久文件目录，后续切对象存储，但无论采用哪一种，媒体必须独立于应用版本发布目录，部署和回滚不得覆盖或删除用户上传。图片备份与数据库备份需要能配套恢复。

## 10. 回复、分享、榜单与收藏

### COMMENT-01：回复评价（原版迁移 + 归属完善，P2）

依据：S02 的 `addReply`、`repliesHtml`、`normalizeReview`。

- 登录用户可回复仍公开有效的评价，初期保留单层回复，不实现无限层级楼中楼。
- 正文去首尾空白后 1–200 个 Unicode 字符，纯文本；作者和发布时间由服务端确定。
- 回复不参与四维评分和推荐率，不改变父评价原发布时间；支持稳定排序和分页。
- 原版归一化只保留末尾 50 条回复，V2 不沿用静默截断，应使用分页保留合法历史内容。
- 支持按钮发送，桌面可提供回车发送；输入法组合输入期间不能误触发发送。
- 作者与管理员可以删除有权处理的回复，管理员恢复能力按统一回收站规则设计。
- 父评价或餐厅删除后不可继续回复，回复内容也不能绕过父状态直接读取。

**验收标准**：回复成功跨设备可见；多次回复不改变店铺评分；无权删除被拒绝；第 51 条及后续回复不静默丢失；父资源恢复时不复活独立删除的回复。

### SHARE-01：分享和复制地址（原版迁移 + 链接完善，P1）

- 餐厅详情可复制名称、地址与摘要；浏览器剪贴板不可用时提供可手动复制的文本。
- 建议分享包含可直接打开的餐厅详情链接；新设备访问后能定位同一餐厅，不只复制当前首页。
- 已删除餐厅的旧链接给出不可用提示；不泄露回收站内容。
- 分享内容不包含 JWT、会话 ID、校园邮箱、管理员配置或用户精确位置。

### RANK-01：杯型餐厅榜（原版迁移，P2）

依据：S02 的 `openRanking`。

- 保留按杯型分组、每档默认前 3 家的展示，并提供综合分、评价数与详情入口。
- 待评级组可保留作为发现入口，但不能称为高分排行；是否单独展示见 D09。
- 同组按原始综合分降序，同分按稳定名称与 ID；必须展示评价数量，避免把一条评价的高分当成充分样本。
- 删除内容不入榜；停业店是否排除、是否设置最低评价数门槛，见 D09。未确认前不要自行引入加权评分或商业置顶。
- 榜单与公开详情使用同一评分规则；缓存后也必须在合理时间内响应发布、修改、删除与恢复。

**验收标准**：8.55 仍归超大杯组；并列结果稳定；没有评价时不出现虚构高分；点击可打开正确餐厅。

### RANK-02：用户贡献榜（原版迁移 + 身份调整，P2）

依据：S02 的 `contribStats`、`openContrib`。原版实际按昵称合并，不以设备 ID 分组。

- V2 建议以账号 ID 统计，显示名仅用于展示；同一账号跨设备合并，两个重名账号分开。
- 保留评价数 → 新增店铺数 → 回复数的降序比较，最终使用稳定账号 ID 破同分；前三名可展示奖牌。
- 默认展示前 10 名，已登录用户未进前 10 但有贡献时补充“我的排名”。
- 仅统计符合公开规则的有效内容，测试数据不统计。未能绑定账号的旧内容保留历史作者，但不冒算成某个现有用户贡献。
- 改显示名不切分历史贡献；删除、恢复和归属审核后计数更新。
- 是否公开停用账号的历史排名、是否引入时间区间，见 D05、D09。

**验收标准**：同名不同账号不合并；改名不丢贡献；删除或恢复不重复计数；界面不展示邮箱或设备标识。

### FAVORITE-01：个人收藏（V2 新增，P2）

- 登录用户可收藏/取消收藏有效餐厅，在个人收藏列表中按收藏时间查看。
- 收藏属于账号，跨设备一致；同一用户与同一餐厅最多一条有效收藏，重复请求有稳定结果。
- 收藏关系不计入评分或推荐率，默认不公开他人的收藏列表。
- 餐厅删除后，收藏列表显示“餐厅已不可用”或隐藏并提供清理方式，不保留可绕过权限的详情。
- 初期只做一个收藏列表；多个清单、公开清单和协作清单另行排期。

**验收标准**：取消后重开页面不恢复；并发收藏不重复；无法读写他人收藏；删除餐厅不导致整个收藏页报错。

## 11. 内容管理与运营后台

### ADMIN-01：最小内容治理和回收站（原版迁移，最小能力 P1，完整后台 P2）

依据：S03 的 `admin/review`、`admin/restaurant`，以及 S02 的删除、恢复与回收站入口。

1. 管理员通过已有账号权限进入后台，不再输入所有人共用的管理口令；不自动向新注册用户授予管理员。
   首位管理员通过受控运维流程授权到已验证的现有账号，不设置默认共享密码，不开放自助提权，授权变更需要可追溯。
2. 按餐厅、评价、回复提供内容查询与处理入口，显示状态、作者、时间和必要的处理记录。
3. 管理员删除内容需要明确原因，记录操作者、对象、动作、结果和时间；普通用户不获得管理审计读取权。
4. 回收站仅对有权限的管理员开放，支持按类型查询、查看影响、恢复；不能在普通公开 GET 中返回全部已删除数据再由前端隐藏。
5. 处理评价后自动更新评分和榜单；处理餐厅后隐藏其子内容，恢复时遵守独立删除状态。
6. 管理员不能直接修改餐厅综合分、伪造他人的作者身份或以批量导入绕过统计规则。
7. “管理员可以使用”的界面能力必须具有同等服务端授权，不能沿用旧版任意对象数组 upsert。

**发布门槛**：对外开放写评价和图片前，至少已有可用的管理删除与恢复流程，并确认管理员账号配置及权限验证。不能让可发布内容长期没有治理入口。

### ADMIN-02：永久清理与运营配置（原版迁移 + 风险收敛，P2）

- 永久清理为独立高权限操作，默认不作为日常删除方式；执行前预览对象、数量和照片影响。
- 明确可清理的软删除保留期、备份要求及恢复方案；初期没有经过恢复验证时不开放生产永久清理入口。
- 不沿用“一个复选框直接删除所有有效评价照片”的默认流程；若确需全站清图，作为单独范围、权限与确认操作。
- 执行有批次、进度、最终结果和失败明细；重复执行不误删新数据。物理文件清理须检查全部有效引用。
- 地图服务配置初期优先通过受控部署配置管理。若提供后台配置，只允许授权管理员写入，界面仅展示已配置状态和必要的脱敏信息。
- 社团共享口令开关、Supabase 地址/公开写入凭证、旧平台分享码不迁移为 V2 的普通用户配置。
- 账号停用、管理员授权、审核策略、举报处理、操作审计页面按独立需求排期；不能只因已有数据库字段就视为功能完成。

### REPORT-01：举报与处理（V2 新增，P2，待确认）

建议允许登录用户对餐厅信息、评价或回复提交举报，填写原因；限制同一用户重复举报。管理员查看并记录“待处理/已处理/不成立”等结果，不能仅凭举报数量自动删内容或改评分。申诉、通知和匿名举报不纳入第一步，是否需要该功能见 D10。

## 12. 导入、导出、备份与旧数据迁移

### IMPORT-01：收集表导入（原版迁移 + 可信性调整，P2）

依据：S01 的 CSV 解析、表头映射与 `mapReviewRow`，S02 的 `renderImportPreview`、`commitImport`。

**输入与预览**

- 管理员可以粘贴表格文本或上传 CSV/TSV/TXT，下载带 UTF-8 BOM 的模板。初期不要求直接解析 XLSX，也不把腾讯文档分享页当作可直接读取的数据接口。
- 兼容逗号、制表符、分号、双引号包裹、引号内分隔符/换行、双引号转义及常见换行符。
- 支持原版中英文别名：店名/name/restaurant、味道/taste、性价比/value、服务/service、环境/ambience、推荐/verdict、作者/author、点评/text、日期/date 等；完整别名由服务端白名单维护。
- 解析后显示可导入数、错误数、疑似重复数、警告数和逐行原因；默认预览前 5 行，但能下载或查看完整错误清单。
- 预览不写正式业务数据；管理员确认后才执行，原始文件和任务结果有授权范围和保留策略。

**业务规则**

1. 缺店名、非法分数、正文不符合长度等行不得直接写入。
2. 原版缺分默认补 7、推荐判断缺失或不认识时常默认推荐，可能人为抬分；V2 建议默认拒绝不完整评分或未知判断，若开启兼容补值必须显式提示并由管理员确认，见 D11。
3. `8分`、`7/10`、全角数字可在严格规则下转换；`/10`、夹杂歧义字符、无效日期和未来日期等不能被悄悄当作合法历史记录。
   解析后的评分仍须满足0–10和0.5步长；若为兼容旧数据进行取整，必须在预览中展示原值、目标值及影响并获得确认。
4. 店名不存在时可选择创建“待定位”餐厅；同名分店有歧义时必须选择绑定对象，不按名字覆盖。
5. 明确区分“未定位”与“待评级”：有有效导入评价的店即使未定位也应正常计算分数，不能强制显示待评级。
6. 导入评价的历史昵称不等于账号归属，保留导入来源、原始作者、批次与操作人；不得按昵称自动赋给新账号。
7. 导入前展示去重策略，建议结合来源行/外部 ID 与餐厅、作者、正文、日期摘要；不能将所有内容相同的不同真实经历一概覆盖。
8. 确认任务只执行一次，失败后重试不能重复创建已成功的数据；部分成功时必须返回具体结果，并支持只重试失败项。
9. 导入完成后，对受影响餐厅按统一规则重算；不能只更新评价表而让地图与榜单保留旧分。

**验收标准**：预览零写入；错误行原因准确；重复确认不会多导；未知分店不误绑；未绑定历史作者不能获得修改权限；不将缺分或未知推荐无提示计入生产分数。

### BACKUP-01：业务导出与恢复（原版迁移 + 备份完善，P2）

- 全量业务导出为管理员能力，范围明确包含餐厅、评价、回复、来源与状态；不得导出密码哈希、JWT、验证码、密钥或会话。
- 导出包含格式版本、导出时间、数据数量和图片清单。媒体是否单独打包必须在界面说明；只有图片 key 的 JSON 不能称为完整备份。
- 业务导出与系统级备份区分：完整恢复需要匹配的 MySQL 备份、媒体文件和必要的安全配置恢复流程，不能只保留浏览器下载。
- 恢复先做校验和预览，明确新增、冲突和不兼容项，不默认覆盖线上全部数据。
- 不使用用户传入的 `updatedAt` 决定谁能覆盖生产账号归属或管理状态；所有恢复由授权流程控制。
- 大数据量导出可异步执行，下载地址有权限与有效期；取消或失败不影响正常业务读写。
- 发布目录和用户数据目录独立，普通代码发布、失败回滚不得替换业务库或上传文件。

**验收标准**：导出无认证机密；媒体缺失可识别；导入错误文件不破坏现有数据；在隔离环境完成备份恢复演练并核对数量、引用、权限和评分后才称为恢复验收通过。

### MIGRATE-01：原项目数据迁移（独立受控工作，P2，正式切换前必需）

本次不执行迁移。迁移前必须取得授权的数据快照和备份，记录具体来源、格式、数量、导出时间与校验信息。

| 原版数据 | V2 处理要求 |
| --- | --- |
| 餐厅旧 ID、`restaurant_id` | 保留旧 ID 映射，不直接信任外部 ID 作为新权限依据；子引用同步映射 |
| `price`、`price_level`/`priceLevel` | 优先保留具体金额；仅有档位时按 1→15、2→25、3→65、4→120 的旧映射识别为估值，不伪装成精确消费 |
| `lat/lng`、`needs_location` | 确认 GCJ-02，缺失或占位坐标标为待定位，不将假坐标投放地图 |
| `closed`、`deleted` | 分别保留经营状态与软删除状态，不能把旧墓碑当正常数据导入 |
| `owner` 设备 ID、昵称 | 默认只保存历史来源；不按昵称、客户端自报设备 ID 自动绑定账号 |
| 评价、推荐判断、四维分数 | 检查真实来源、范围、步长与字段枚举；剔除或隔离测试/演示数据 |
| `comments` | 拆成独立回复并保留父子关系；旧版本已截断或丢失的记录不能凭空恢复 |
| 图片 dataURL / 本地 key | 校验并转换为受控媒体；只有 key 而没有二进制的列为缺失，不生成假 URL |
| 创建时间、更新时间 | 校验并统一时区；迁移执行时间与历史发表时间分开记录 |
| 本地昵称、共享口令、同步配置 | 不导入为账号密码、角色或生产连接配置 |

**归属策略**：旧系统没有校园邮箱账号映射，历史记录无法仅凭昵称安全认领。建议保留 `legacyAuthor` 等展示信息，归属暂为空或明确的历史身份，仅管理员可维护；后续如做认领，必须有可验证证明和审计，见 D12。

**迁移步骤与验收**

1. 盘点原版服务器数据、浏览器导出和图片来源，识别重叠、墓碑、孤儿和缺失图片。
2. 在隔离环境预检并生成报告，不连接生产库尝试写入。
3. 确认旧 ID 映射、账号归属、分店绑定、分数补值和冲突规则，冻结输入快照。
4. 演练导入和回滚，逐类核对数量、引用、图片可访问性及所有餐厅重算结果。
5. 正式切换时约定停写窗口或受控增量策略；初期不同时维持两套可写主数据。
6. 迁移后按旧 ID 抽样追溯，确认普通用户不能因伪造设备 ID 修改历史数据；保留可恢复备份。

种子目录只可作为经确认的初始餐厅候选，不是已核验营业信息。空库部署不得自动灌入示例评价，也不得在用户清空后自动复活演示数据。

## 13. 数据共享、离线与安装

### SYNC-01：共享数据一致性（重构调整，核心 P1，离线写入 P3）

- 用户在不同设备读取到同一份服务端数据，写入必须经认证、权限、字段校验和数据库事务。
- 新增/修改/删除成功后，当前页主动刷新相关数据，其他设备按重新打开、手动刷新或约定的刷新策略获取最新状态。
- 初期不承诺秒级推送，不要求搬迁原版 Supabase 15 秒轮询和浏览器全量待上传队列。轮询、服务端事件或其他实时方式另行评估。
- 列表、详情、地图和榜单可以缓存，但必须定义可见延迟和失效方式；不能用长期缓存绕过删除、权限和账号状态校验。
- 网络中断时显示读取失败或缓存数据的明确标识。初期禁止把未发送的操作显示为已发布，可保留本地草稿供用户确认重试。
- 如果后续实现离线队列，必须处理账号切换、过期身份、重复提交、版本冲突、失败重试和草稿隐私；不能把 A 账号离线内容自动用 B 账号发布。

### PWA-01：安装与离线阅读（原版迁移，P3）

保留手机和桌面安装体验作为后续目标；需域名、HTTPS、图标、manifest、更新与缓存策略。静态壳与公开只读缓存可分级处理，认证响应、用户私有数据、管理接口和退出请求不能被 Service Worker 当作永久成功响应缓存。升级或注销时，不允许旧缓存把已退出的账号重新显示为已登录。

## 14. 业务对象与状态约束

以下是逻辑对象要求，用于指导设计，不是已存在的数据表或最终建表 SQL。新增结构必须使用新的 Flyway 迁移，禁止修改已执行脚本。

| 对象 | 最小信息 | 关键约束 |
| --- | --- | --- |
| 餐厅 | ID、名称、分类、人均、地址、坐标系与坐标、标签、经营状态、待定位、来源、创建者、时间、删除信息 | 不使用编辑版本；综合分不是用户填写字段；经营状态与删除分离；位置未知不伪造 |
| 评价 | ID、餐厅 ID、作者账号或历史作者、四维分数、推荐判断、正文、来源、版本、时间、删除信息 | 四维完整，账号归属由服务端确定；不能关联不可发布的餐厅 |
| 回复 | ID、父评价 ID、作者、正文、时间、状态 | 独立归属；父状态限制读取与新增，不参与评分 |
| 评分结果 | 餐厅 ID、有效评价数、单条总分合计、各维度合计、推荐数、计算版本/时间 | 可从评价重建；缓存或汇总不成为独立可手工改分的数据源 |
| 文件 | 文件 ID、上传者、用途、媒体属性、存储标识、状态、时间 | 绑定校验与引用检查；客户端不能控制物理路径 |
| 收藏 | 用户 ID、餐厅 ID、收藏时间 | 用户与餐厅组合唯一，属于私有账号资源 |
| 导入批次 | 批次 ID、操作人、文件摘要、预览结果、确认参数、处理状态、成功/失败明细 | 防重复确认，原始来源可追溯，禁止借导入伪造账号归属 |
| 操作记录 | 操作人、对象、动作、结果、原因码、时间、必要的变更摘要 | 不含密码、验证码、JWT、密钥、完整敏感请求体 |
| 旧 ID 映射 | 来源标识、旧实体类型/ID、新 ID、批次 | 支持幂等迁移与子引用追溯，不是用户权限凭证 |

### 14.1 状态与父子关系

- 餐厅至少区分正常营业、停业；软删除作为独立状态/字段，不与停业合并。
- 评价与回复至少区分正常和软删除。发布前审核尚未确认，不提前假设已有待审核状态。
- 公开读取先检查父餐厅、父评价的可见性，再判断子内容；不能仅根据文件 URL 或子记录 ID 公开访问。
- 删除父对象不直接覆写每个子对象的独立删除记录；恢复父对象只恢复符合自身状态的子内容可见性。
- 汇总的有效集合、列表可见集合、导出包含范围和贡献统计范围应明确区分，不能都使用“全部记录”一词。
- 业务修改时间、历史发表时间、迁移时间和管理处理时间分别记录；对外时间使用现有 API 的 ISO 8601 UTC 约定。

### 14.2 事务、并发与重试

- 评价写入与对应统计更新要么在事务中一致完成，要么采用有明确定义的可靠更新与重建机制；不能先报告成功再永久漏算。
- 餐厅删除与并发发布评价必须由服务端再次核对，不能只在打开表单时检查一次父状态。
- 餐厅编辑采用最后成功保存覆盖，不比较客户端版本或时间；保留归属/当前删除状态校验和主表/标签事务，删除后的普通PUT不能复活记录。其他资源的版本/冲突策略按所属阶段设计，不因餐厅调整自动改变。
- 网络超时不等于写入失败，发布、导入确认、文件绑定等操作需有幂等或结果查询机制。
- 文件处理和数据库事务不能假设为一个原子事务，需要可重试的绑定、过期和清理流程。
- 提供从有效评价重建评分的受控能力，用于迁移和排障；重建后与在线计算口径一致。

## 15. 模块边界与实现约束

沿用 Java 21、Spring Boot 4、MyBatis-Plus、MySQL、Redis、Flyway、Spring Security，以及 Vue 3、TypeScript、Vite、Pinia 的既有基线。当前采用模块化单体，一个后端进程，不为本轮需求预先拆微服务。

| 模块 | 拥有的数据与职责 | 跨模块协作方式 |
| --- | --- | --- |
| `user` | 账号、邮箱验证、账号状态、角色归属、账号公开资料 | 提供公开账号查询/校验服务；不向业务模块暴露密码哈希或 Mapper |
| `security` | JWT、Redis 会话、认证与授权、登录保护 | 业务模块读取已认证身份；不直接操作用户模块数据表 |
| `restaurant` | 餐厅目录、分类标签关系、位置、经营和删除状态 | 提供有效餐厅查询、发布许可与目录变更接口/事件 |
| `review` | 评价、回复、评分计算与可重建的统计 | 通过餐厅公开服务检查父对象；对外批量提供评分结果 |
| `file` | 文件元数据、上传、处理、受控访问、清理 | 业务模块通过公开服务校验/绑定文件，不直接操作文件 Mapper |
| `admin` | 管理操作编排、后台权限、管理任务与必要的操作记录 | 调用对应业务应用服务处理删除/恢复，不直接改其他模块表 |
| 收藏能力 | 建议独立 `favorite` 模块，按阶段引入 | 仅保存收藏关系，通过公开服务检查餐厅，不反向修改评分 |
| 榜单/导入能力 | 先按真实规模决定放在所属领域或独立读模型/任务模块 | 不在 `common` 或 `system` 中堆放业务逻辑，不横跨 Mapper |

具体包和表名在各阶段设计中确定。Controller 只做协议与参数转换，Entity 不作为接口请求/响应；新增或修改的类、公共方法、配置与关键安全/并发逻辑按项目规则提供中文注释。

M1首批表结构见[餐厅模块表结构设计](architecture/restaurant-schema.md)，包括分类字典、餐厅主表和餐厅标签。V3及既有测试保留，只初始化13类，不自动导入餐厅或评价。餐厅CRUD已实现；写入金额、标签总码点数、当前操作者、归属及删除状态均校验，主表和标签同事务更新。用户已取消餐厅版本号，V3原有row_version列保留但应用不读取、比较或递增；不修改已有迁移。前端分类/列表/详情及新增/编辑/删除已接入，回收站页面待做；本地开发库已升级并手动加入模拟数据，生产库尚未升级。

餐厅列表不能逐条查询评价造成查询数量随列表条数线性增加；评分和作者信息应通过批量应用接口或合适的读模型获取。缓存属于技术优化，不能替代权限判断。

## 16. 后续接口能力清单

本节餐厅分类、列表、详情，以及新增/编辑/软删除/管理快照/按ID恢复已在当前工作区实现，其余仍为**计划能力**。实际已实现URL见 [api.md](api.md)，餐厅接口尚未部署；只读接口已接入前端，写入表单未实现，不将后续能力当成已可调用接口。

| 能力 | 认证与范围 | 重要副作用或限制 |
| --- | --- | --- |
| 餐厅分页查询、详情、分类字典（本地已实现） | 公开只读；D01已确认未登录可浏览餐厅 | 删除与私有管理字段不公开；全局筛选计数和分页一致；前端已接入 |
| 地图视口点位、地点检索 | 只读；外部地点服务需独立配额限制 | 地图点位上限与列表分页分开，不返回服务端地图密钥 |
| 新增/修改餐厅、软删除（本地已实现） | 登录；编辑/删除仅创建者或管理员 | 校验身份、归属与当前删除状态，无需版本；主表和标签事务保存，最后成功保存生效；后续接入点位/缓存时补齐失效处理 |
| 餐厅评价分页、评分摘要 | 与餐厅阅读权限一致 | 摘要基于全部有效评价，不基于当前页 |
| 发布/修改/删除评价 | 登录；修改和删除仅本人或有权管理员 | 权限、状态、幂等、评分更新、图片绑定 |
| 回复分页、新增、删除 | 阅读随父内容；写入需登录和归属校验 | 不影响评分，父资源失效则拒绝新增 |
| 上传临时图片、文件访问/解绑 | 登录及用途/归属约束；公开读取服从父状态 | 文件数量、媒体校验、生命周期与访问控制 |
| 我的内容、收藏操作 | 登录，仅本人 | 不允许客户端切换 userId 读取他人私有资源 |
| 榜单 | 建议公开只读 | 排序稳定，统计与公开有效集合一致 |
| 回收站、管理删除/恢复 | 管理员专属；餐厅按ID恢复已实现 | 校验当前删除状态，不要求餐厅版本；回收站分页、审计及评价聚合变更待做 |
| 导入预览、确认、进度、明细 | 具有数据导入权限的管理员 | 预览不写入，确认防重，结果可追溯 |
| 导出、恢复、永久清理 | 独立高权限 | 完整范围、备份和媒体引用检查 |

通用约束：分页有上限，排序参数采用白名单；服务端不依赖前端校验；失败沿用统一响应。公开阅读请求的客户端策略应按方法/路径明确配置，防止残留过期 JWT 阻塞原本公开的阅读能力。

状态码原则沿用：参数问题 400，身份缺失/失效 401，权限不足 403，不存在或不可对外展示的对象 404，状态/版本冲突 409，频率限制 429，依赖暂不可用 503。具体业务错误码以实际新增枚举为准，本文不提前宣称尚不存在的错误码。

## 17. 非功能需求与质量门槛

### 17.1 安全与隐私

- 所有业务修改默认需要认证，公开读取仅在安全配置中按方法显式允许。
- 账号归属、角色、分数、图片归属、导入权限均在服务端校验，界面隐藏不是授权。
- 正文、回复、标签、导入预览和文件名不执行用户 HTML；图片验证不能只看扩展名或浏览器 `Content-Type`。
- JWT、密码、验证码、私钥、SMTP 和地图服务端凭据不进入 Git、响应正文或日志。普通业务页不展示邮箱、设备 ID 等内部标识。
- 认证与内容发布的限流策略分别定义，按账号和必要的网络维度约束，不能仅靠客户端倒计时。
- 域名与 HTTPS 为后续对外使用的部署强化项；当前 `localStorage` + Bearer 的限制要保留记录，不将其描述为 HttpOnly Cookie 方案。
- 管理操作具备最小授权和可追溯记录；是否提供审计查询页面与具体保留期另行评审。

原版通用数组upsert不能作为V2的授权模型：`server.js`中通用写入主要检查共享口令，并未按账号核验每条资源归属；`/api/mapkey`写入分支也未见管理员会话校验。V2必须按新权限矩阵重新实现这些边界，不因兼容旧页面而保留原有缺口。

### 17.2 可用性与交互

- PC、手机均可完成核心流程，390px 宽度无水平溢出；不把重要操作仅放在鼠标悬停状态。
- 输入有标签和明确错误，状态变化有可读提示；键盘能到达主要按钮，弹层可关闭并恢复合理焦点。
- 页面区分“无数据”“筛选无结果”“加载中”“服务失败”“地图不可用”，不能把网络失败显示为 0 家餐厅。
- 提交和管理操作防重复，危险操作展示对象与影响；失败保留合理的可重试输入，不显示虚假成功。
- 地图与图片故障不能让正文、评分和餐厅列表不可读。表单离开与登录切换时合理处理草稿和敏感内容。

### 17.3 性能、容量与运维

以下为建议验收目标，需在相应阶段固定测试数据和环境后确认，不是已达到的性能结论：

- 初期压测样本建议至少 1000 家餐厅、10000 条评价，以约 20 个并发只读请求验证分页与统计不会全表回传。
- 普通列表/详情 API 的服务端响应 P95 可先以不超过 800ms 为目标，排除外部地图服务等待；记录硬件、数据量、缓存冷热和错误率后评估。
- 地图按视口/上限取数、评价与回复分页、图片按需加载；不能将全部照片 base64 随列表传输。
- 明确分页最大值、文件大小与像素上限、单次导入行数、下载有效期和任务超时，不使用无限制参数。
- 数据库升级可重复部署并校验迁移版本；发布失败保留已验收版本，程序回滚不逆向删除用户新数据。
- 上传与备份存储不放在应用发布版本目录；健康、版本与任务失败可定位，但公开探针不暴露配置详情。
- 旧版“几千条以内可用”的经验不能代替 V2 实测；也不因更换数据库就默认承诺任意规模。

### 17.4 测试要求

- 单元测试覆盖评分边界、状态转换、导入转换和权限相关业务分支。
- Mapper/集成测试覆盖真实 MySQL 约束、事务、并发更新与必要的 Redis 原子行为；不能把按条件跳过写成通过。
- 接口测试覆盖身份、所有权、管理员权限、字段校验、失效父资源、幂等和异常响应。
- 前端测试覆盖真实表单交互、加载错误、重复提交、分页筛选、多标签页和迟到请求保护。
- 浏览器验证至少包含桌面和手机、地图失败降级、跨账号越权失败、发布后另一设备可读、删除恢复及改密后的旧会话失效。
- 真实地图、真实邮件、真实存储等外部能力的验收须与模拟 API 测试分开记录。
